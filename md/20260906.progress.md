## 2. Downstream biology on the 6 sane donors, chr1

Built fresh (not present in the codebase before today): `nearest_snp_dist` per significant
region, computed against each donor's own `vcf/read_based/{sample}_chr1_het_snps.vcf.gz`
(nearest-neighbor search via `np.searchsorted` on sorted het-SNP positions). Classification
follows the phase-1 rule from `notebooks/asm_analysis/W07_classify_annotate_wg.ipynb`
(proximal ≤200bp, distal ≤5kb, very-distal >5kb), with one substitution made explicit rather
than silent: `ont_asm_caller`'s `significant`/`qval<0.05` stands in for the old pipeline's
AUC/Mann-Whitney `read_level_support` test, which `ont_asm_caller` doesn't compute (it uses a
beta-binomial LRT on region means, a different statistic).

**Proximal/distal split** (4,922 significant regions pooled across 6 donors): 50.5%
proximal, 46.0% distal, 3.5% very-distal. Roughly balanced — notably different in framing
from phase-1's 81.8% "non-genetic" HG01258 result, though that's not a clean apples-to-apples
comparison given the different `read_level_support` proxy and different basecaller/cohort.

**Effect size by category** (median `|delta|`): proximal 0.192, distal 0.186, very-distal
0.178 — **essentially identical across categories**. This replicates phase-1's W10 finding
(distal loci are not functionally weaker than proximal ones) in an independent 6-donor,
different-basecaller cohort — a genuine cross-cohort replication worth highlighting in any
write-up.

**Cross-donor replicability**: only 36% of a donor's significant regions overlap ≥1 other
donor's; 16.5% overlap ≥2 of the other 5. Read this as *expected*, not concerning — it's the
predicted signature of genotype-driven ASM (a locus only shows ASM in a donor actually
heterozygous at the driving SNP, so non-overlap is often just "different donor, different
het site," not non-replication). The imprinting comparison below is the direct test of this
logic.

**Imprinting overlap (the most interesting single result so far)**: of the 4 known chr1
parent-of-origin DMRs (Zink et al. 2018), **3 of 4 show significant ASM hits in 5-6 of the 6
donors** — far above the 36% background replicability rate. Imprinted loci (parental origin,
not genotype-specific) are expected to replicate near-universally across donors regardless of
which SNP each donor happens to carry, while ordinary genotype-driven loci should replicate
only among donors who share the relevant het site — and that is exactly the qualitative
split observed. This is a clean, mechanistically-motivated positive control that the
beta-binomial caller is behaving sensibly, independent of the deCODE-rate comparison.

Full per-region tables: `tables/dasm_betabinom/{sample}/regions_chr1.tsv` (per-project repo,
not mirrored here — see main repo for raw data).

## 4. The HG00344/NA21144 dispersion anomaly — investigated, not yet resolved

Checked directly against the other 6 (sane) donors:

- **Coverage** (`qc/mosdepth/*.summary.txt`): HG00344 = 56.35x, the *lowest* of all 8 good
  donors (next-lowest sane donor, NA19700, is 69.61x — a real ~20% gap). **NA21144's
  mosdepth summary file is genuinely 0 bytes** (confirmed directly, not just referenced from
  the prior "minor and unrelated" dismissal) — its coverage is simply unknown right now, not
  low-but-known. This should be rerun before drawing any conclusion about NA21144 specifically.
- Lower coverage alone seems too small an effect to explain a 60-100x dispersion inflation
  (a ~20% depth gap causing a 2-orders-of-magnitude dispersion jump would be a very
  nonlinear, surprising relationship) — treat coverage as a plausible *contributor* for
  HG00344, not a full explanation, and as simply unassessed for NA21144 until mosdepth is
  rerun.
- **Het-SNP density** (chr1): HG00344 = 332,846, NA21144 = 341,593 — both squarely in the
  normal range (307k-400k across all 8) — rules out "too few informative sites" as an
  explanation for either sample.
- **HP-tag rate** (chr1:1-20Mb, direct `samtools view` count): NA19700 (sane) = 33.1%,
  HG00344 = 44.4%, NA21144 = 46.4%. This is the opposite direction from what a naive
  "worse phasing = fewer tagged reads" hypothesis would predict — **but this is a weak test
  of the actual leading hypothesis**, which is not about how many reads get an HP tag, but
  whether HP1-in-one-phase-block corresponds to the same physical haplotype as
  HP1-in-the-next-block (a switch-error / phase-block-consistency question). A read can be
  confidently HP-tagged locally and still contribute to inflated apparent dispersion if
  blocks are internally inconsistent — raw tag rate doesn't distinguish this. **No
  whatshap-stats-style phase-block output exists yet in this project**; that's the concrete
  next check, not something already ruled out by the HP-tag numbers above.
- Not yet checked: whether these are two independent single-sample data-quality issues, or a
  shared cause (e.g. both from the same sequencing batch/facility/run — worth a quick
  metadata cross-check against `csv/meta/cohort_downloads.tsv` before assuming they're
  unrelated).

**Bottom line**: not resolved. Coverage (HG00344) and a missing QC file (NA21144) are real,
concrete, unglamorous candidate contributors, not exotic ones — this looks more like ordinary
HPRC long-read data-quality heterogeneity (uneven per-sample coverage, an incomplete QC run)
than a flaw in the beta-binomial method itself, but the switch-error/phase-block check is the
one that would actually settle it and hasn't been run.

## 5. Truncated-sample fix — status

`bam/merged_bam`, `bam/haplotagged`, and `modkit/` stale outputs for the 6 affected samples
(HG00126, NA20762, HG00253, NA19776, HG03784, NA20870) have been removed. **`pileup/` stale
outputs for the same 6 samples have not** — these must go too before resubmitting, or `W03`
will silently keep the old (truncated-derived) pileup data (all downstream stages skip on
bare file existence, not content). New driver script,
`scripts/wg/fix/resubmit_6_truncated_samples.sh`, chains
`W00a -> W00b -> W01_phase_per_chrom -> W01g -> W02 -> W03` with per-stage task IDs verified
directly against each stage's own manifest/sample-list file, and refuses to submit (printing
the exact remaining `rm` command) while stale output is still present — this is deliberate,
not a bug: per project convention, cleanup is done by hand, never automatically as part of a
resubmit.

Rough wall-clock estimate once cleanup finishes (chained, sequential stages; see also
timing notes shared in chat) — dominated by `W01_phase_per_chrom` (whole-genome whatshap
haplotagging, one task per sample, no direct timing logs survived from the original June run
to confirm empirically) and `W03` (modkit pileup, empirically **highly variable, up to
2-4.3 hours for a single large-chromosome task** based on surviving logs) — **plan for
roughly 1-2 days of mostly-unattended wall-clock**, not continuous active attention.
